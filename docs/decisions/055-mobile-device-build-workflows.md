# ADR-055: Manually built phone test packages for real devices

## Status

Accepted for Android, 2026-10-17. The iOS hosting and distribution decision is superseded by
[ADR-057](057-local-ios-builds-and-device-privacy.md), 2026-10-20; the original decision and revision below are historical
for iOS. The original request was for GitHub APK and registered-device IPA builds without a version bump or preview release.

## Context

Testing currently happens on the maintainer's own phones; TestFlight and Google Play test tracks are not in use yet.
The existing Apple workflow produces only unsigned packages, which cannot be installed directly. A new Android debug key
generated by every CI run would also stop updates over the existing app and would not match the registered Google
OAuth signature.

## Decision

- Add `android-apk.yml` and `ios-ipa.yml`, built only by manual dispatch on main; the token is contents: read.
  They create no tag/Release, upload to no store and change no version number; the packages and their SHA-256 are kept
  as Actions artifacts for fourteen days.
  Artifact names include the platform version, run ID and attempt, and a text file in the package records the source
  commit, to tell apart different builds of the same version.
- Android uses the fixed existing debug keystore, for testing only. CI restores it temporarily from a Secret and after
  the build checks `WORK_FLEET_ANDROID_DEBUG_SHA1`; on a signature mismatch the APK is not kept. Production Play
  signing/OAuth is prepared separately.
- iOS uses an Apple Development identity and two development profiles, for the main app and the Share Extension.
  It first checks the Team/App ID/App Group, the main app's Keychain group, validity periods, the certificate and that
  both profiles register the same device set.
  After compiling an unsigned Debug build, the signing tool signs the dylibs/frameworks/Extension/app in order and
  embeds each one's profile.
  This also supports existing Xcode-managed profiles without CI signing in to the Apple account; the local Xcode project
  settings are unchanged.
- Private keys and keystores live in GitHub Secrets; the runner uses a temporary keychain/files and removes
  them in an always step. Private signing keys are never written to public configuration, the repository or artifacts.
  Provisioning profiles are also restored from Secrets, but become readable inside a signed IPA after embedding;
  their device identifiers are not protected by the Secret or by choosing not to create a Release.
  Authorization to send credentials to GitHub and each workflow dispatch are obtained separately.
- The IPA is limited to the devices registered in the profiles and is installed from a Mac with Xcode/Apple
  Configurator, with Developer Mode enabled on the device.
  After adding a device, update the profiles of both the main app and the Extension, then build again.

## 2026-10-17 revision: optional GitHub prereleases

The maintainer asked for Android and iOS previews to be published on GitHub like the desktop previews.

- Both workflows gain a `release` input, off by default. Off, they behave as above. On, they first refuse a version
  whose tag or release already exists (`android-v<versionName>`, `ios-v<MARKETING_VERSION>`) and read that version's
  entry in [release notes](../release-notes.md); after the package is built, signed and verified, a separate job with
  contents: write creates the prerelease with the installer and its SHA-256. A failed run publishes nothing.
- Publication follows the same rules as the desktop previews (AGENTS.md, [deployment](../deployment.md)): the version
  bump and its release-notes entry come first, dispatch needs the maintainer's authorization, and a published tag or
  release is never moved or replaced.
- The Android APK stays signed with the fixed test key and the IPA stays development-signed for the registered
  devices; neither is a store build.

## 2026-10-23 revision: the APK goes into the shared release

The Android `release` input and its `android-v<versionName>` prerelease are gone. Dispatched by hand, `android-apk.yml`
only builds a device APK. `preview-release.yml` calls it with the release commit and publishes the verified APK and its
SHA-256 in the one `v<version>` release that carries every platform
([ADR-044](044-desktop-in-app-updates-from-github-releases.md)); the same authorization and no-bookkeeping rules apply.

## Consequences

### Positive

- Test packages for the maintainer's own devices can be provided continuously, keeping updates over the existing phone
  apps and the Google OAuth signature consistent.
- Source commits, manual builds and the formal test/store channels can each be verified, without creating a public
  Release for every build.

### Negative

- The iOS certificate/profile validity periods and device list need upkeep; Actions artifacts are not a permanent
  download site.
- Having the GitHub workflows written does not mean they have run in the cloud or that a phone has accepted the
  build; missing Secrets fail explicitly.
- A signed IPA embeds its development profiles, which list registered device identifiers (UDIDs); both a public
  prerelease and a public repository's Actions artifacts expose them. ADR-057 replaces this iOS hosting approach.
- Phone prereleases share the repository's release feed with the desktop updaters (ADR-044). Each updater only reads
  its own tag prefix, but the Atom feed lists only the most recent releases, so many phone-only releases in a row
  could push the newest desktop release out of it; the per-platform update index ADR-044 leaves open would remove
  that limit.

## Alternatives Considered

- Keep the unsigned IPA: cannot be installed directly on the specified phones, which does not meet this request.
- Generate an Android debug key automatically in every CI run: cannot keep updates over the existing app or the OAuth
  configuration.
- Adopt TestFlight/Play internal testing right away: kept as a later direction; this round uses test packages for
  specified devices.
