# ADR-055: Manually built phone test packages for real devices

## Status

Accepted, 2026-10-17. The user asked for GitHub build workflows for an APK and an IPA for specified devices, with no
version bump and no preview release.

## Context

Testing currently happens on the maintainer's own phones; TestFlight and Google Play test tracks are not in use yet.
The existing Apple workflow produces only unsigned packages, which cannot be installed directly. A new Android debug key
generated by every CI run would also stop updates over the existing app and would not match the registered Google
OAuth signature.

## Decision

- Add `android-apk.yml` and `ios-ipa.yml`, built only by manual dispatch on main; the token is contents: read.
  They create no tag/Release, upload to no store and change no version number; the packages and their SHA-256 are kept
  as Actions artifacts for fourteen days.
  Artifact names include the platform version, run ID and attempt, and a text file in the package records the source
  commit, to tell apart different builds of the same version.
- Android uses the fixed existing debug keystore, for testing only. CI restores it temporarily from a Secret and after
  the build checks `WORK_FLEET_ANDROID_DEBUG_SHA1`; on a signature mismatch the APK is not kept. Production Play
  signing/OAuth is prepared separately.
- iOS uses an Apple Development identity and two development profiles, for the main app and the Share Extension.
  It first checks the Team/App ID/App Group, the main app's Keychain group, validity periods, the certificate and that
  both profiles register the same device set.
  After compiling an unsigned Debug build, the signing tool signs the dylibs/frameworks/Extension/app in order and
  embeds each one's profile.
  This also supports existing Xcode-managed profiles without CI signing in to the Apple account; the local Xcode project
  settings are unchanged.
- Private keys/keystores/profiles live only in GitHub Secrets; the runner uses a temporary keychain/files and removes
  them in an always step.
  Secrets are never written to public configuration, the repository or artifacts. Authorization to send credentials to
  GitHub and each workflow dispatch are obtained separately.
- The IPA is limited to the devices registered in the profiles and is installed from a Mac with Xcode/Apple
  Configurator, with Developer Mode enabled on the device.
  After adding a device, update the profiles of both the main app and the Extension, then build again.

## Consequences

### Positive

- Test packages for the maintainer's own devices can be provided continuously, keeping updates over the existing phone
  apps and the Google OAuth signature consistent.
- Source commits, manual builds and the formal test/store channels can each be verified, without creating a public
  Release for every build.

### Negative

- The iOS certificate/profile validity periods and device list need upkeep; Actions artifacts are not a permanent
  download site.
- Having the GitHub workflows written does not mean they have run in the cloud or that a phone has accepted the
  build; missing Secrets fail explicitly.

## Alternatives Considered

- Keep the unsigned IPA: cannot be installed directly on the specified phones, which does not meet this request.
- Generate an Android debug key automatically in every CI run: cannot keep updates over the existing app or the OAuth
  configuration.
- Adopt TestFlight/Play internal testing right away: kept as a later direction; this round uses test packages for
  specified devices.
